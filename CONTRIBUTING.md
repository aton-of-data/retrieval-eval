# Contributing

The project is a **specification with two reference implementations**. That shapes everything
below: a change is not done when one language passes, it is done when both agree.

## Setup

```bash
pnpm install                                    # TypeScript
pnpm -r build && pnpm -r test

cd python/retrieval-eval                        # Python
python3 -m venv .venv && ./.venv/bin/pip install -e ".[dev]"
./.venv/bin/pytest
```

Then the check that actually matters:

```bash
./python/retrieval-eval/.venv/bin/python scripts/check_parity.py
```

It runs both CLIs over every shared fixture and compares three things: JSON reports as data,
human-readable output and every help screen byte for byte, and the stderr of failing invocations
along with the exit code. Run it with the **same interpreter that has the package installed**.
With any other one it stops before doing anything and tells you so.

Help text, error wording and rendered output are part of the contract, not decoration. A change
to any of them lands in both implementations in the same commit, or parity fails.

## Generated files, which are never hand-edited

Two kinds of file in this repo are derived. Editing a copy directly means your change is silently
reverted by the next build, and CI will fail before that:

| Generated | From | Regenerate with |
|---|---|---|
| `packages/*/README.md`, `python/*/README.md` | `README.md` | `pnpm readme` |
| `packages/*/spec/`, `python/*/spec/` | `spec/` | `pnpm sync:spec` |

`pnpm check:consistency` verifies both, plus that the version agrees in all four places it is
written (two manifests, two `TOOL_VERSION` constants).

Edit the root `README.md`. Variant blocks (`<!--:npm-->`, `<!--:pypi-->`, `<!--:root-->`) pick
which copies a passage lands in; unmarked prose goes everywhere. Relative links are rewritten to
absolute GitHub URLs for the registry copies, because npmjs.com and pypi.org resolve them against
nothing.

## The rule

**Every behaviour change starts in `spec/`.**

1. Add or change a fixture in `spec/fixtures/`.
2. Watch **both** test suites fail.
3. Make both pass.
4. `check_parity.py` must stay green.

A change that only lands in one language is a bug, even if its tests pass. `spec/fixtures` is
the source of truth; the implementations are the claim.

## Adding a metric

1. Add expected values to `spec/fixtures/basic/expected.json`, **computed by hand or by an
   independent reference**, never by the code under test. A fixture generated by the
   implementation it tests proves only that the code is self-consistent.
2. Implement in `packages/retrieval-eval/src/metrics.ts` and
   `python/retrieval-eval/src/retrieval_eval/metrics.py`.
3. Keep the key order identical to `spec/report.schema.json`. The two implementations emit
   byte-identical JSON for everything except integral-float formatting, and that is worth
   preserving.

## Adding an adapter

Adapters are the whole adoption strategy: the point is that nobody has to switch tools. An
adapter converts some other tool's dataset to or from `judgments.jsonl`.

Wanted: RAGAS, DeepEval (Python and TypeScript), promptfoo, ragbench, Langfuse, Braintrust,
Phoenix, BEIR, `ir_datasets`.

An adapter must:

- round-trip losslessly where the other format allows it, and **say what it drops** where it
  does not;
- preserve unknown fields (the spec requires round-tripping fields you do not understand);
- ship a fixture under `spec/fixtures/adapters/<name>/`.

## Porting the spec to another language

Please do. Go, Rust, Java and Ruby would all be useful. The bar is:

- the `spec/fixtures/chunk-id` vectors pass, so your `chunk_id` agrees byte for byte;
- every other fixture passes;
- `scripts/check_parity.py` grows a third command and stays green.

If you find the spec ambiguous enough that two honest implementations could disagree, that is a
spec bug. Open an issue rather than guessing. Those reports are the most valuable contribution
to this project.

## Style

- **Zero runtime dependencies.** Both packages. A measurement tool that drags in a dependency
  tree becomes a thing people skip installing in CI. Dev dependencies are fine.
- **No LLM calls anywhere in this repo.** The judged half of evaluation belongs to RAGAS and
  DeepEval; this package computes what can be computed deterministically and stays cheap enough
  to run on every commit.
- **Never invent ground truth.** `drift --fix` re-anchors labels whose exact text still exists
  and refuses to touch `SPLIT` or `ORPHANED`. Any feature that guesses at a label is out of
  scope, however convenient.
- **Warnings are a feature.** A statistically unsound judgment set that parses cleanly is the
  failure mode this tool exists to catch. If you can detect one, add a warning.
- **Prose is plain.** No em dashes, no repeated claims across files, one canonical home per
  fact and a link from anywhere else that needs it.
- TypeScript: `biome check --write .`, `tsc` strict with `noUncheckedIndexedAccess` and
  `exactOptionalPropertyTypes`. Python: `ruff`, `mypy --strict`, Google-style docstrings.
- **Coverage floors.** `vitest.config.ts` and the pytest `--cov-fail-under` gate in CI hold the
  suites near where they are today. Raise them, never lower them.

## Where documentation lives

| | |
|---|---|
| `spec/` | the formats and the hash. The contract, and the only thing a port needs |
| `README.md` | what the tool is and why, plus the canonical table of problems it removes |
| `docs/` | CLI reference, CI recipes, interoperability, troubleshooting |
| `research/` | the evidence behind the positioning |

Put a fact in exactly one of those and link to it from the others.

## Commits and releases

Conventional commits. TypeScript releases go through `changeset`; the Python version lives in
`pyproject.toml`. **Both packages release together with the same version**. A spec version that
means two different things in two registries defeats the point.
